# JUNCTION-REALISM — trace findings (Stage 0/1)

**Status:** MEASURED. Every number below comes from a committed instrument on a committed scenario and
is reproducible offline except where SUMO is named. No fix is proposed here; §5 lists what is
established versus what is still an open question.

**Reported defects being chased** (owner, this session): gridlock; lateral lane change while standing
at a red, sometimes into an already-occupied lane; two cars visually merged inside a junction; two cars
driving through each other when one is turning left and the other going straight.

---

## 1. The repro

`scenarios/_diag/junction-realism-L{1,2}` (+ `-light`), generated by
`scripts/gen-junction-realism-net.py`. A 2×2 grid of traffic-light junctions 80 m apart; the four
internal links form a cycle; each junction is a 4-way with two external stub arms; the generated TL
program has a permissive-left phase. Insertions stop at t=600 and the run continues to t=1800, so
"did it clear?" is decidable — a merely busy network empties once inflow stops.

Demand is calibrated against honest SUMO rather than guessed, because an oracle that itself gridlocks
proves nothing. Sweeping the demand scale: scale 1 gridlocks **honest SUMO itself** (97–124 vehicles
never clear); scale 2 congests it hard (mean trip 261 s against ~90 s free-flow) but **always drains**.
Scale 2 is the committed operating point; scale 4 is the `-light` control.

## 2. The headline

Identical net, identical routes, both engines run to t=1800 (1200 s after the last insertion):

| run | arrived | running | halting | meanSpeed | |
|---|---|---|---|---|---|
| SUMO-honest L1 | **450** | **0** | 0 | — | DRAINED |
| engine L1 `--parity` | 60 | 225 | 225 | **0.000** | GRIDLOCK |
| engine L1 coordinated-LC | 60 | 225 | 225 | 0.000 | GRIDLOCK |

| engine L2 coordinated-LC | 188 | 262 | 262 | 0.000 | GRIDLOCK |

It reproduces in `--parity` mode, so this is the **core engine**, not the product-default coordinated
lane-change model; and at **both lane counts**, so it is not
`NEED-multilane-junction-passage.md`'s multilane over-yield.

## 3. Where it localises

`scripts/analyze-junction-realism-fcd.py`, run on both engines' FCD (same schema, so the numbers are
directly comparable — that is the point of using FCD on both sides):

| | engine `--parity` | SUMO-honest |
|---|---|---|
| stopped-inside-junction samples | 27 629 (7.73%) | 559 (0.48%) |
| vehicles ever stranded inside a junction | 39 | 44 |
| **longest dwell inside a junction** | **1660 steps** | **29 steps** |
| OBB overlap pairs at t_end | **4** (one per junction, all BOTH-INTERNAL) | **0** |
| junction-interior overlap, ever | J01 t=50, J11 t=84, J00 t=140, J10 t=106 | **never** |

**A vehicle stranding inside a junction is not itself the defect — SUMO strands 44 of them.** The
difference is that SUMO's always resolve (≤29 s) and ours never do. And SUMO never once has two cars
interpenetrating inside a junction, across the whole run.

**Causal order (the question the owner's report raises).** Both readings were live: "two cars overlap
and everything queues behind them" (overlap → wedge) versus "a car strands and later arrivals pile in"
(wedge → overlap). They predict opposite time orders, so the timestamps settle it: **overlap comes
first at 3 of the 4 junctions** (J01 t=50 vs wedge t=140; J11 t=84 vs t=154; J00 t=140 vs t=210), and
the overlaps are early in absolute terms. J10 is the exception (wedge t=94, overlap t=106). ⚠ This
establishes *precedence*, not *causation* — see §5.

## 4. The mechanism, from a per-vehicle SUMO diff

The first junction-interior overlap in the whole run is at **J01, t=50**, between
`f_cyc_ccw2.0` (westbound, **turning LEFT** onto `v0r`) and `f_cyc_cw2.1` (eastbound, **straight**
through). That is exactly the owner's fourth defect: *"one standing in the middle of a junction trying
to turn left and the other going straight."*

Step-by-step, same two vehicle ids in both engines:

| t | ours: `f_cyc_ccw2.0` | ours: `f_cyc_cw2.1` | pen | SUMO: `f_cyc_ccw2.0` |
|---|---|---|---|---|
| 48 | `:J01_5_0` pos 1.60 spd 2.60 | `in_W01_0` pos 184.60 | 0 | `:J01_5_0` pos 3.97 spd 0 |
| 49 | `:J01_5_0` pos 3.97 spd 2.37 | `in_W01_0` pos 192.40 spd 7.80 | 0 | `:J01_5_0` pos 3.97 spd 0 |
| **50** | **`:J01_13_0` pos 4.87 spd 4.97** | `:J01_10_0` pos 10.00 spd 10.40 | **1.94 m** | `:J01_5_0` pos 3.97 **spd 0** |
| 51 | `:J01_13_0` spd 0.00 | `h1_0` pos 6.43 | 0 | `:J01_5_0` pos 3.97 spd 0 |
| … | | | | holds until t=56, then proceeds |

SUMO holds the left-turner **in the bay for 10 s** (t=47…56) and lets the opposing straight through.
We admit it to stage 2 at t=49→50 and interpenetrate.

**Named mechanism.** The relevant gate is `InternalJunctionAdmissionConstraint`
(`Engine.cs:7878`, `InternalJunctionAdmissionGate`, default **ON** — verified, not assumed). Its
structure is correct and its data is correct:

* `:J01_13_0` is an internal junction whose checker (first `incLanes` entry) is the bay `:J01_5_0`,
  parent link index **5**, `cont=1` — matching `MSInternalJunction::postloadInit`;
* `response[5] = 111110000110` has bit **10** set, so `:J01_10_0` — the lane the opposing straight
  crossed on — *is* a legitimate foe lane;
* our parse agrees: `InternalLaneFoes[:J01_13_0]` contains `:J01_10_0` (probed directly).

**The gate does not fire because at the decision step the foe lane is EMPTY.** At t=49 the foe is
still at `in_W01_0` pos 192.40 — one step upstream of the conflict lane. The gate's foe test is
`_neighborQuery.OnLane(foeLaneHandle)`, a physical-presence scan, so `Count == 0` → `continue` → not
blocked → ego is admitted, and the foe arrives on the conflict lane in the same step it does.

This is a **documented, deliberate omission**, not an oversight to discover: `Engine.cs:7791-7797`
states that the port implements the `myInternalLaneFoes` half of
`MSLink::setRequestInformation` and that *"there is no further approach/WillPass refinement (that is
`myInternalLinkFoes`, the omitted half)."* SUMO's split is precisely lanes = "who is standing in my
way" versus links = "who is approaching and will be in my way". **The trace says the omitted half is
the load-bearing one for this defect.**

## 5. What is established, and what is not

**Established.**
1. The engine gridlocks permanently where honest SUMO fully drains, on identical inputs, in parity
   mode, at both lane counts.
2. We interpenetrate inside junctions; SUMO never does on this net.
3. Our junction strandings are unbounded (1660 steps) where SUMO's are transient (≤29).
4. The first interpenetration is caused by admitting a cont-turn vehicle from its stage-1 bay into
   stage 2 against a foe that is approaching but not yet on the foe lane, and the omitted
   `myInternalLinkFoes` half of SUMO's split is exactly the mechanism that would have held it.

**NOT established — do not write these down as facts.**
1. **That fixing the admission gate dissolves the gridlock.** Overlap precedes wedge at 3 of 4
   junctions, which is suggestive and nothing more; precedence is not causation (CLAUDE.md lesson 15
   is a case where exactly this reasoning produced an answer that was wrong by 5-of-9 versus 0-of-9).
   The gridlock may be an independent circular wait that the overlap merely decorates. **This is
   settled by an experiment, not by argument**: implement the approach arm, re-run §2 and §3, and see
   whether `arrived` moves. If overlaps go to 0 and the network still gridlocks, the two defects are
   independent and the gridlock needs its own trace.
2. ~~**That J10 fits the same story.**~~ **TRACED — it is CASCADE PROPAGATION, not a second root
   cause.** See §7.
3. **Anything about the other two reported defects.** The lane-change-at-red-into-occupied defect
   (`SUMOSHARP-ISSUE-stopped-lane-change-overlap.md`) has not been looked for on this net yet; nor has
   the pedestrian-held-in-junction amplifier the owner described, which cannot be tested through
   `Sim.Run` at all (no ped coupling on that path — it lives in `LiveCitySim`).

## 6. Instruments (committed — use these, do not re-derive)

## 7. J10 resolved — cascade propagation, plus one NEW open question

§5.2 flagged J10 as the junction that does not fit: it wedges (t=94) *before* it overlaps (t=106).
Traced `f_cyc_ccw2.3`, the vehicle whose stall defines that wedge, in both engines.

**The two engines are bit-identical up to t=91** — same wait on `in_S10_0` at pos 191.80 through t=89,
same entry onto `:J10_7_0` at t=90 (pos 1.60, spd 2.60), same t=91 (pos 6.80, spd 5.20). They diverge
at the junction **exit**:

| t | ours | SUMO |
|---|---|---|
| 91 | `:J10_7_0` pos 6.80 spd 5.20 | `:J10_7_0` pos 6.80 spd 5.20 |
| 92 | `:J10_7_0` pos 11.95 spd 5.15 (decelerating) | **`v1_0` pos 0.20 spd 7.80** (accelerating, clear of the junction) |
| 93 | `:J10_7_0` pos 12.61 spd 0.65 | `v1_0` pos 8.40 spd 8.20 |
| 94+ | **stopped at pos 12.61 forever** — ~0.2 m short of the lane end | continues, queues on `v1_0` at pos 47.07 — *outside* the junction |

The exit link `v1_0` explains it. At t=91:

* **ours** — 8 vehicles, **every one at speed 0.000**, front vehicle at pos **5.7** (i.e. the queue
  reaches back to the junction exit), and the whole link is **still frozen at t=92, 93, 94**;
* **SUMO** — 6 vehicles, front at pos 19.6, and the queue is **discharging**: `f_cyc_ccw.0` moves at
  t=91, `.1` at t=92, `.2` at t=93, `.3` at t=94 — a textbook backward discharge wave.

`v1_0` runs J10 → J11, and **J11's own junction-interior overlap occurred at t=84**, ten seconds
earlier. So J11's wedge stopped `v1_0` discharging, `v1_0` backed up into J10's exit, and
`f_cyc_ccw2.3` stranded inside J10. The order across the net is a **cascade**:

    J01 t=50  ->  J11 t=84  ->  J10 t=94 (wedge)  ->  J00 t=140

This removes §5.2 from the open list and *strengthens* the overlap-first reading — but it still does
not prove causation, and the `-light` control (which overlaps 3 times yet drains completely) remains
the standing reason not to promote it. See the tracker.

### NEW open question this raised — a possible keep-clear gap, NOT yet a claim

At t=90 our vehicle **entered** `:J10_7_0` while its exit link already held 8 fully-stopped vehicles
with the nearest only 5.7 m past the entry. Entering a junction you demonstrably cannot clear is what
SUMO's `checkRewindLinkLanes` exists to prevent, and we have `KeepClearConstraint` (`Engine.cs:7345`,
binder 11) which is *supposed* to protect ego's own downstream exit. **Why it did not fire here is not
known and has not been investigated.**

Two reasons not to treat this as a second confirmed defect yet:

1. **It may be downstream.** By t=90 the run has already diverged from SUMO (since J01 at t=50), so
   our `v1_0` queue state is not the state SUMO faced. SUMO never had to refuse this entry, so this
   trace cannot show what SUMO would have done — it shows only what *we* did.
2. **It is exactly the reasoning shape that has failed here before.** Naming a mechanism from one
   suggestive observation, without a trace of the constraint's own decision, is what produced seven
   refuted interventions. The next step, if this is picked up, is the **binder tag at t=90** for that
   vehicle — did `KeepClearConstraint` evaluate and permit, or was it never consulted? — not a source
   reading.

## 8. The approach arm's verdict — it fixes admission and EXPOSES the missing other half

Measured with `scripts/run-net-regression.py` over 26 committed nets, **both arms re-run with the same
(split-dwell) instrument** — reports in `docs/reports/net-regression-{baseline,approach-arm}.txt`.

**Where it wins:**

| | arm OFF | arm ON |
|---|---|---|
| junction-realism-L2 arrived | 139 | **320** |
| junction-realism-L2 still running | 310 | **130** |
| junction-realism-L2 `stuckDwell` | 956 | **597** |
| junction-realism-L2 peak overlap pairs | 9 | **7** |
| the traced J01 seed case | 1.94 m interpenetration | **byte-identical to SUMO, t=50…58** |
| goldens | — | **661 byte-identical**, parity 776/4 |

**Where it loses, and this is the important part.** On `city-organic` the arm makes junction overlaps
**worse**: 255 → **296** overlap events (+16%), peak simultaneous pairs 3 → 5 (`city-organic-L2`: 4 → 5).
Dumping the pairs shows a signature that is *new* in the arm-ON run:

    2.302 m  t=503   veh165 [:359_11_0] spd=0.00   x   veh212 [:359_10_0] spd=10.25
    2.302 m  t=501   veh165 [:359_11_0] spd=0.00   x   veh208 [:359_10_0] spd= 8.52

A vehicle **held stationary inside the junction** — which is exactly what this arm does, correctly, by
design — being **driven through at 8–10 m/s by cross traffic**.

**So the two halves need each other.** The approach arm stops ego entering a junction into an
approaching foe's path. It does nothing about the converse: cross traffic driving through a car that is
*already* stopped inside the junction. Before the arm, cars did not linger in bays, so the second
failure had fewer opportunities; holding them correctly creates them. The arm did not introduce the
drive-through mechanism — the same class is present at baseline (`veh93 spd=0.41 x veh183 spd=5.28`) —
it increases its *frequency*.

That missing converse is `Engine.JunctionPhysicalOccupancyGate`, which exists, is **default OFF**, and
is recorded as *"measured counterproductive three times; do NOT retry alone"* (`F3-SESSION-LOG.md` §5).
**This measurement is the first evidence for why it was counterproductive alone and what it needs to be
paired with.** The natural reading: an occupancy gate without the approach arm makes admission more
conservative with nothing to gain; the approach arm without an occupancy gate creates stationary
targets. Neither is a fix by itself. **This is a hypothesis generated by the measurement, and it is
NOT yet tested** — the experiment is the pair, on both surfaces, and it has not been run.

### Recommendation, and what is NOT claimed

`InternalJunctionApproachArm` should **not** ship default-ON on this evidence. It is parity-clean and it
more than doubles throughput on the repro, but it degrades a real committed net on the exact metric
(visible interpenetration) that motivated the workstream. The honest options are (a) default OFF pending
the paired experiment, or (b) default ON only inside a high-realism zone, where the owner's constraint
already says artefacts are unacceptable and where the paired occupancy gate belongs anyway.

**Not claimed:** that the pair fixes the gridlock. The arm alone did not — L1 went 60 → 63 arrived and
both nets still deadlock, against SUMO's 450/450. Whatever holds L1 solid remains untraced, and §7's
keep-clear question is still the best lead.

## 9. The paired experiment — §8's hypothesis is REFUTED

§8 read the evidence as "the approach arm and `JunctionPhysicalOccupancyGate` are two halves of one
mechanism; neither works alone." That was written down as an untested hypothesis. **It has now been
tested, as a full 2×2 with both gates set explicitly in every cell (CLAUDE.md #10), and it is wrong.**

Overlap EVENTS (every overlapping pair, every step — not the peak-simultaneous summary §8 used):

| cell | arrived | running | overlap events |
|---|---|---|---|
| L1 arm OFF occ OFF | 60 | 225 | 6467 |
| L1 arm OFF occ ON | 55 | 224 | 3207 |
| L1 arm ON occ OFF | 63 | 226 | 6464 |
| L1 arm ON occ ON | 54 | 227 | 3204 |
| **L2 arm OFF occ OFF** | 139 | 311 | 12751 |
| L2 arm OFF occ ON | 83 | 333 | 9316 |
| **L2 arm ON occ OFF** | **320** | **130** | **313** |
| L2 arm ON occ ON | **61** | 327 | 3223 |
| SUMO-honest (both) | 450 | 0 | 0 |

**The pair is far WORSE than the arm alone.** On L2 the occupancy gate takes arrivals from **320 down
to 61** — below even the do-nothing baseline of 139. It costs throughput in every combination it
appears in (139 → 83 with the arm off; 320 → 61 with it on). That is the fourth independent measurement
finding this gate counterproductive, and the first showing it is counterproductive *paired* as well as
alone. **Do not re-attempt the pairing without new evidence.**

**Two corrections this experiment forces on §8:**

1. **§8's "two halves of one mechanism" reading is retracted.** The occupancy gate does roughly halve
   overlaps everywhere (L1 6467→3204, L2 12751→3223 with the arm on), so its *stated* purpose works —
   it simply buys that with a ruinous amount of throughput. It is not the arm's missing partner.
2. **§8 understated the arm badly, because it used the wrong summary statistic.** Peak-simultaneous
   pairs moved only 9 → 7, which looked marginal. Total overlap events on the same runs moved
   **12 751 → 313, a 97.5% reduction.** A peak is a poor summary of a duration-weighted phenomenon;
   the event count is the honest one. **The arm alone is by a wide margin the best cell measured.**

### Where that leaves the recommendation

The arm alone: repro L2 arrivals **+130%**, overlap events **−97.5%**, goldens **661 byte-identical**,
parity 776/4 — against one real committed net (`city-organic`) where overlap events rise 255 → 296.
That residual is now the ONLY thing standing between this change and a default-ON ship, and it needs its
own trace (§7's keep-clear question is the standing lead — `city-organic` is also the net with a 68-step
junction dwell). Pairing it with the occupancy gate is no longer a candidate answer.

**Still not fixed, and still not close:** the gridlock. The best cell leaves 130 vehicles permanently
stopped on L2 and 226 on L1, against SUMO's 0. Every measurement in this document has moved overlaps;
none has moved the deadlock.
