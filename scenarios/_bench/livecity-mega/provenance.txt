# Net-sizing exploration (why grid15/500m/-L2, not the task's suggested starting point of a
# 40x40/200m grid):
#   - First attempt: --grid.number=40 --grid.length=200 -L 2 (same flags otherwise) ->
#     extent 7,816.8 m, 67,999 lanes (1,600 junctions; the 200 m block spacing plus guessed
#     sidewalks/crossings/walkingareas at every junction multiplies element count heavily).
#     Car capacity was fine (4,821-4,920/5,000 achieved, no gridlock, no lane-connection
#     exception). BUT pedestrian spawning was the bottleneck: LiveCityConfig.ForSumocfg uses
#     RouteGraph ped nav (SumoRouteGraphNav), and its per-spawn route search cost scales with
#     ped-graph size -- profiled at ~390 ms/step for only ~12 ped spawns/step (--profile:
#     ped.spawnDue = 93-99% of wall). At the ped_spawn_rate this net's population needs, that
#     is far too slow to fill 20,000 peds in any practical number of steps/wall-clock time.
#   - Root cause is JUNCTION COUNT (hence ped-graph size: every junction adds crossings +
#     walkingareas + connections), not block length or total lane-km. Re-tested at
#     --grid.number=15 --grid.length=500 (225 junctions vs 1,600, ~7x fewer) with the same
#     -L2 + sidewalks/crossings/walkingareas: ped.spawnDue dropped roughly proportionally
#     (~79 ms/step for the same ~12 spawns/step at grid15 vs ~390 ms/step at grid40), and at
#     production scale reached the FULL 20,000 peds in just 39 fill-steps.
#   - Car capacity was NOT sacrificed by shrinking junction count: grid15 (8,999 lanes,
#     extent 7,016.8 m) still reached 4,872-4,920/5,000 cars with no gridlock (still growing
#     at the fill-steps cutoff, not saturated) -- i.e. capacity tracks total lane-km/extent,
#     not junction density, while ped-routing cost tracks junction/ped-graph density. This is
#     why the shipped net favours FEWER, LONGER blocks (grid15/500m) over the task's literal
#     40x40/200m suggestion.
#   - -L2 (2 lanes/direction) was kept throughout: the PERF-HANDOVER.md Sec.5 / city-3000-
#     provenance "No lane on edge ... has a <connection> to ..." NetworkModel.ResolveSequenceCore
#     defect was NOT observed on this net across all measurement runs (up to ~4,920 concurrent
#     cars over 1,000+ steps) -- reported per the task instructions even though it did not fire,
#     so a future session does not have to re-derive that -L2 was tried and was fine here.
